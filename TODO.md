## Ядро для інтеграцій і ліцензій

Мета: lego вбудовується на чужі сайти й кастомізується без правок ядра. Ліцензія продається на ядро, і підтримка теж лише на ядро: публічний API, формат проєкту й міграції, сумісність із браузерами, документація. Типи меблів клієнта, форми, теми, інтеграції та сервер клієнта в підтримку не входять.

Порядок: рішення → відв'язка від сторінки → пілот → продукт. Загальну платформу наперед не будуємо: публічний API уточнюємо за тим, що знадобиться пілоту.

### Рішення перед стартом

- [ ] Хто робить кастомізацію: розробники клієнта, партнери чи ми за окрему плату. Від цього залежить обсяг документації та прикладів.
- [ ] Кого беремо пілотом: один виробник меблів зі своїм сайтом.
- [ ] Модель ліцензії: на домен, на виробника чи на обсяг; що входить в оновлення й підтримку, скільки підтримуємо стару мажорну версію. Договір і обмеження відповідальності за помилки в розмірах погодити з юристом.

### Етап 1. Відв'язка від сторінки

Ці задачі корисні й без ліцензій. Готово, коли дві копії конфігуратора працюють на одній сторінці незалежно, а `index.html` запускає lego так само, як сайт клієнта.

- [x] **Запуск через API.** `createConfigurator(root, options)` повертає екземпляр із `destroy()`. Зараз запуск виконується під час імпорту `main.js` (`createViewer`, `initSidebar`, `initToolbar`, `initModal`, `initReport`). `main.js` має лише викликати `createConfigurator`. `destroy()` звільняє WebGL, слухачі подій і таймери. Перевірка: e2e зі створенням, знищенням і повторним створенням.
- [x] **Стан екземпляра.** `store` у `core/store.js` — один об'єкт на модуль, він читає `localStorage` під час імпорту. Потрібно `createStore(options)`, щоб кожна копія мала свій стан. Форми, сайдбар, тулбар і звіт отримують стор від екземпляра, а не імпортують його. Тести `core/` оновити разом зі зміною.
- [x] **Сховище як опція.** Адаптер `storage: { load, save }`, за замовчуванням `localStorage` з ключами `lego-project` і `lego-preset`. Клієнт може вимкнути його або зберігати проєкт у своїй базі. Старий ключ `wardrobe-cfg-v1` і далі читається з міграцією.
- [x] **Розмітка всередині `root`.** `$` шукає в `document`, а в `index.html` 29 статичних `id`. Розмітку конфігуратора генеруємо шаблоном у `root`, усі пошуки обмежуємо ним, хуки переводимо на `data-*`. Те саме для `translateDom()` і модалки. E2E оновити разом із хуками.
- [x] **Мова екземпляра.** `locale` і власні словники як опції; перемикач мов можна вимкнути. Запис у `lego-locale` — лише через адаптер сховища.

Правила шарів не змінюються: загальні модулі не знають про конкретні типи. Перевірка: тестовий тип поза `src/js/core/types/` проходить контрактні тести `core/registry.test.js`.

### Етап 2. Пілот

Готово, коли конфігуратор працює на сайті клієнта без форка ядра, а кожна зміна для клієнта зроблена через опції, тип або хук.

- [ ] **Вбудувати на сайт пілота** й вести журнал: що довелося змінювати в ядрі і чому. З цього журналу формуємо публічний API.

- [ ] **Ціни через адаптер.** `quote(request)` замість фіксованої адреси API; контракт запиту й відповіді беремо з пункту «Контракт і інтеграція з API прорахунку вартості». Кошик і замовлення лишаються на боці клієнта (`onOrder`).
- [ ] **Налаштування виробника.** Матеріали, формат листа, обрізка, зазори, пороги перевірок і пресети як опції.
